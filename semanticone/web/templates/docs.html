Quick start

  1. Create a workspace. It comes with the Acme Commerce sample model attached to a sample warehouse.
  2. Open the model and go to Explore. Pick metrics and dimensions and press Run.
  3. Create an API key under API & AI agents and connect an AI agent through MCP, or call the REST API.
  4. On a paid plan, add a warehouse connection, upload your own model and attach the connection in model settings.

Semantic models

Models use the Apache Ossie core format (version 0.2.0.dev0): one model per YAML or JSON document with datasets, fields, relationships and metrics. Documents in the older 0.1 shape with a semantic_model wrapper are migrated automatically.

version: 0.2.0.dev0
name: Sales
datasets:
  - name: orders
    source: analytics.public.orders      # table, view, or a SELECT query
    primary_key: [order_id]
    fields:
      - name: order_id
        expression: {sql: id}            # written over source columns
      - name: ordered_at
        expression: {sql: created_at}
        datatype: DateTime
        dimension: {is_time: true}
      - name: amount
        expression: {sql: amount_cents / 100.0}
  - name: customers
    source: analytics.public.customers
    primary_key: [customer_id]
    fields:
      - name: customer_id
        expression: {sql: id}
      - name: country
        expression: {sql: country_code}
        dimension: {}
relationships:
  - name: orders_to_customers
    from: orders            # the many side
    to: customers           # the one side
    from_columns: [customer_id]
    to_columns: [customer_id]
metrics:
  - name: revenue
    expression: {sql: SUM(orders.amount)}   # model metrics use dataset.field
    ai_context: {synonyms: [sales, GMV]}

Expressions are chosen per engine: an entry in dialects matching your warehouse (for example SNOWFLAKE) wins, otherwise the portable sql / OSSIE_SQL_2026 / ANSI_SQL form is translated to the warehouse's SQL dialect. Opaque dialects such as DAX or MAQL are stored but not executed.

Every save is validated (JSON Schema plus name resolution: keys, relationships and metric references must point to declared fields). Errors block the save; warnings tell you what cannot be queried yet.

Query format

{
  "metrics": ["revenue", "orders.order_count"],      // model metrics, or dataset.metric
  "dimensions": ["customers.country", "orders.ordered_at__month"],
  "filters": [
    {"field": "orders.ordered_at", "op": ">=", "value": "2026-01-01"},
    {"field": "customers.country", "op": "in", "value": ["US", "CA"]},
    {"field": "revenue", "op": ">", "value": 1000}    // metric filters apply after aggregation
  ],
  "order_by": ["-revenue"],
  "limit": 100
}

Time grains: hour, day, week, month, quarter, year (as a __grain suffix or {"field": ..., "grain": ...}). Filter ops: =, !=, >, >=, <, <=, in, not_in, between, like, not_like, is_null, is_not_null. Values are always sent as bound literals, never spliced as SQL.

How results stay correct

Relationships point from the many side to the one side. The engine evaluates every aggregate inside a metric from a dataset it aggregates (its root) and joins only along many-to-one paths from there, so rows are never duplicated. When a query mixes metrics from different fact tables, each root is aggregated separately by the requested dimensions and the results are combined on those dimensions. Duplicate-insensitive aggregates (COUNT(DISTINCT ...), MIN, MAX) may be rooted further out when needed, which is how "orders containing a product category" is answered.

If a question cannot be answered without double counting (for example, support tickets by product category when tickets don't link to products), the query is refused with an explanation rather than returning an inflated number. Window metrics such as running totals are supported; they require grouping by the fields used in their window.

REST API

Send Authorization: Bearer so_live_.... Interactive reference: /api/docs.

curl -s {{ settings.base_url }}/api/v1/models/acme-commerce/query \
  -H "Authorization: Bearer $SEMANTICONE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"metrics": ["total_revenue"], "dimensions": ["orders.ordered_at__month"]}'
EndpointPurpose
GET /api/v1/modelsList models
POST /api/v1/modelsCreate a model from {"content": "...yaml..."}
GET /api/v1/models/{slug}Metrics, dimensions and relationships
GET|PUT /api/v1/models/{slug}/documentDownload or save a new version (CI-friendly)
POST /api/v1/validateValidate a document without saving
POST /api/v1/models/{slug}/compileGet SQL for a query
POST /api/v1/models/{slug}/queryRun a query, get rows
GET /api/v1/usagePlan limits and usage

AI agents (MCP)

SemanticOne is a remote Model Context Protocol server at {{ settings.base_url }}/mcp (Streamable HTTP). Authenticate with an API key as a bearer token. Tools: list_models, describe_model, query_metrics, compile_sql, validate_model.

Claude Code:

claude mcp add --transport http semanticone {{ settings.base_url }}/mcp \
  --header "Authorization: Bearer $SEMANTICONE_API_KEY"

Clients that take a JSON config (Cursor, Claude Desktop via mcp-remote, and others):

{
  "mcpServers": {
    "semanticone": {
      "url": "{{ settings.base_url }}/mcp",
      "headers": {"Authorization": "Bearer so_live_..."}
    }
  }
}

Write good description and ai_context (instructions, synonyms, examples) on metrics and fields: agents read them through describe_model.

Warehouse connections

Paid plans can connect PostgreSQL, Redshift, Snowflake, BigQuery, Databricks SQL and MySQL with a SQLAlchemy URL. Use a read-only role limited to the schemas your models use. Credentials are encrypted with a key held only by the application. Hosts that resolve to private networks are blocked on the hosted service.

Importing from other tools

The Apache Ossie project publishes reference converters for dbt, Snowflake, Databricks, Cube, Salesforce/Tableau, ThoughtSpot, Sigma, Omni, Hex, Holistics and others at apache/ossie-converters. Convert your existing semantic layer to Ossie YAML with them, then upload the file here or PUT it to the API from CI. Downloads are plain Ossie, so models move the other way just as easily.

Security

  • Passwords hashed with scrypt; API keys stored as SHA-256 hashes and shown once.
  • Warehouse credentials encrypted at rest (Fernet / AES-128 + HMAC).
  • Every query is a single generated SELECT; model expressions cannot contain statements or subqueries, and filter values are literals, never SQL text.
  • The sample warehouse runs in a sandboxed, read-only DuckDB with file and network access disabled.
  • CSRF protection on every form, secure session cookies over HTTPS, workspace isolation on every query.
